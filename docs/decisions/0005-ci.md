# 0005: CI layout, and what MLX can use on GitHub's macOS runners

**Status:** accepted · **Task:** M0-T6

## The question F2 asked first

Does MLX run on GitHub's hosted macOS runner, and on the GPU or only the CPU? `scripts/mlx_probe.py` answers it on any machine. Its output from the `mlx` job is attached to every run as the `mlx-probe` artifact and shown in the job summary.

**Answer, from CI run 43704494663 on image `macos26` version 20261102.0473.1:** MLX 0.32.4 runs, and **it runs on a GPU**. The runner exposes a paravirtualized Metal device:

| | Hosted `macos-26` runner | The author's machine |
|---|---|---|
| CPU | Apple M1 (Virtual), 3 cores | Apple M4, 10 cores |
| Memory | 7.5 GB | 16 GB |
| Metal device | "Apple Paravirtual device", about 5.0 GB recommended working set | Apple M4, about 12.7 GB |
| MLX default device | GPU | GPU |
| bf16 1024×1024 matmul, sum of absolute values | GPU 26,781,138; CPU 26,781,016 | GPU 26,781,138; CPU 26,781,014 |

The matmul timings in the probe are one-shot and are not benchmarks. The useful result is the last row: the hosted GPU produced the same bf16 result as the M4's GPU, and both differ from the CPU path. This replaces the assumption in the architecture walkthrough (panel 11) that the CI runner has no GPU.

Consequences for the equivalence suite:

- CI can run the real model on a GPU. Qwen3-0.6B in bf16 (about 1.2 GB of weights) fits the roughly 5 GB working set; Qwen3-1.7B (about 3.4 GB) might fit, but leaves little room, so CI stays on 0.6B.
- One matching matmul does not prove that whole-model greedy output matches across the two GPUs. M0-T7 tests that directly: the `mlx` job regenerates the goldens with mlx-lm and compares them with the ones committed from the author's machine. If they diverge, CI compares uLLM against mlx-lm run on the same runner instead, and the committed goldens stay the reference for local runs.
- With 3 virtual cores and a paravirtualized GPU, CI timings mean nothing. No benchmark runs in CI.

## CI layout

One workflow, `.github/workflows/ci.yml`, with four jobs. All are to be required on `main`; turning on branch protection is the author's call.

| Job | Runner | Runs |
|---|---|---|
| `core` | `ubuntu-24.04` | `uv sync --locked`; asserts MLX is absent; ruff check and format; strict mypy; `pytest -m "not mlx"` with the hypothesis `ci` profile |
| `mlx` | `macos-26` | MLX probe (artifact and summary); `pytest -m mlx` |
| `router` | `ubuntu-24.04` | gofmt, `go vet`, `go test -race` |
| `terminal` | `ubuntu-24.04` | `pnpm install --frozen-lockfile`; generated contract types fresh; strict typecheck |

- **Triggers:** every pull request, whatever its base, so stacked pull requests get CI; pushes to `main`; manual dispatch.
- **Pinned actions:** every action is pinned to a commit SHA, with the release named in a comment. Releases newer than about two weeks were skipped (`pnpm/action-setup` is on 6.1.0, not 6.1.1).
- **Least privilege:** `permissions: contents: read`. A newer push to the same pull request cancels its running checks.
- **`macos-26` over `macos-15`:** it is the hosted image closest to the author's macOS 27, and it is what `macos-latest` points to.
- **Why `core` asserts MLX is absent:** it proves the platform markers work, so a passing `core` job really means the core needs no MLX.
- **Later jobs:** `evals` arrives with Q7 (M4-T3). The router chaos test joins `router` in M5-T1. The terminal's lint, test and build steps join `terminal` with its scaffold in M1-T8.
