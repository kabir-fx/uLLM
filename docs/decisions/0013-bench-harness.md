# 0013: The benchmark harness, workload A, and run conditions

**Status:** accepted · **Task:** M1-T6 (B1, B2, B5)

## Context

M1-T7 measures uLLM against `mlx_lm.server`, and M2-T6 sweeps concurrency. Both need one harness that drives any OpenAI-compatible server the same way (rule 7), writes C5 result directories, and refuses runs whose conditions make the numbers meaningless (B5). Nothing in the repo measures a served request yet: `make bench-smoke` exits 2.

Facts this design rests on:

- Both targets accept `stream_options.include_usage`, `chat_template_kwargs` and `max_tokens`, and serve `GET /health` (`mlx_lm/server.py` lines 1300, 1330, 1683, 1793 in mlx-lm 0.32.2; C1 for uLLM).
- Neither has `GET /metrics` yet. uLLM gains it in M2-T5.
- `powermetrics` must run as root (`powermetrics -h` on macOS 27.2.1). `--format plist` writes NUL-separated property lists.
- `pmset -g batt` names the power source, and `pmset -g` prints `lowpowermode`. Neither needs root.
- `HfFileSystem` from `huggingface_hub` 2.4.0 streams a dataset file at a pinned revision, so a workload builder can read the first rows of a 964 MB file without downloading it (2,000 rows in 18 s, measured).

## Decision

**Layout.** `bench/` holds the harness as plain modules, run with `uv run python -m bench.<module>`:

| Module | Owns |
|---|---|
| `bench/schema.py` | The pydantic shapes of the workload file and of every C5 file |
| `bench/loadgen.py` | The closed-loop client: concurrency N, raw SSE, a timestamp per content chunk |
| `bench/conditions.py` | Observing B5 conditions, deciding whether a run may start, the `powermetrics` process |
| `bench/run.py` | One run, end to end: launch, health, warm-up, repeats, cooldowns, files |
| `bench/analysis.py` | `summary.md` and `latency.svg` per run; a comparison table across runs |

`bench/make_workload_a.py` builds `bench/workloads/a.json` (`uv run python -m bench.make_workload_a`). It lives in `bench/`, not `scripts/`, so it can import `bench.schema`.

**Workload A (B2).**

- Source: `stingning/ultrachat`, MIT licence, `train_0.jsonl` at revision `f220fe79`, read in order. UltraChat dialogues are generated by two models, so no real user's text enters the repo.
- A request is a dialogue prefix that ends with a user turn: the first 1, 3 or 5 turns, whichever is the longest that renders to at most 1,000 prompt tokens. Prompts under 100 tokens are skipped.
- Prompt tokens are counted with uLLM's own `MLXTokenizer.render` on the pinned Qwen3-0.6B tokenizer, thinking off, and stored per request. A dialogue whose rendering changes when control-token text is sanitized is skipped, so `mlx_lm.server`, which does not sanitize, renders the same ids (decision 0011).
- `max_tokens` is drawn uniformly from 50 to 300 with a seeded `random.Random`.
- 256 requests. A run may take the first N.
- Measured on the committed file: every request is a 5-turn prefix; prompts run from 155 to 793 tokens, median 461; the `max_tokens` budgets sum to 45,988. The file is 671 KB, and a second build reproduced it byte for byte (SHA-256 `a8983061`).

**The C5 run directory.** One directory per run: one target, one concurrency, measured under B5. A run holds one discarded warm-up and R measured repeats over the same requests in the same order.

| File | Content |
|---|---|
| `config.json` | Target name, base URL, launch command, served model id from `GET /v1/models`, workload path and SHA-256, request count, concurrency, repeats, warm-up count, cooldown, sampling (`temperature` 0), `chat_template_kwargs`, `smoke` |
| `env.json` | Commit and whether the tree was dirty, chip, cores, memory, macOS, Python and library versions, power source, battery level, Low Power Mode, whether `powermetrics` ran, running containers, the top ten processes by CPU, start and end times |
| `raw.jsonl` | One line per request: `phase` (`warmup` or `measure`), `repeat`, request id, send time from run start, every content chunk's arrival time in ms after send, end time, `usage`, `finish_reason`, `error` |
| `metrics.txt` | `GET /metrics` after the last repeat; absent when the target returns 404, and `summary.md` says so |
| `powermetrics.plist` | The `powermetrics` log; absent on a smoke run |
| `target.log` | The launched target's stdout and stderr |
| `summary.md`, `latency.svg` | Written by `bench.analysis` |

**Metrics (B3's per-request set, computed by `bench.analysis` from `raw.jsonl` only).**

- TTFT: the first content chunk's time. A role-only chunk is not content.
- TPOT: (last chunk − first chunk) / (`completion_tokens` − 1), from `usage`, so a chunk that carries several tokens does not distort it. Undefined for one-token replies.
- End-to-end latency: end time.
- Output tokens per second per repeat: the sum of `completion_tokens` over the repeat's wall time, from the first send to the last end.
- p50 and p99 by nearest rank, over all measured requests. Each repeat's figures, and the median over repeats, are reported.
- Fairness: the count of replies whose `prompt_tokens` differ from the workload's, and of failed requests. Both should be 0.

**Run conditions (B5).** A full run refuses to start unless all hold, and prints each failure:

- on AC power, Low Power Mode off;
- `sudo -n true` succeeds, so `powermetrics` can log (the author runs `sudo -v` first);
- no running Docker containers (the compose stack is stopped);
- at least 3 repeats, at least 1 warm-up request, a cooldown above 0 s (default 120 s, from the original spec).

Other apps cannot be checked, so `env.json` records the top processes instead. `--smoke` skips the checks and records `smoke: true`. `bench.analysis` heads a smoke summary with "smoke: not a B5 run".

**`make bench-smoke`.** Launches `ullm serve` on the default model, runs the first 16 requests of workload A at concurrency 1, 2 warm-up requests, 1 repeat, no cooldown, into `bench/.scratch/`, and prints the summary. It took 81 s on the M4, model load included.

## Alternatives considered

- **ShareGPT as the prompt source.** vLLM's serving benchmark uses it. It holds real users' conversations scraped from the web, which this public repo would then republish. UltraChat has the same chat shape without that problem.
- **`HuggingFaceH4/ultrachat_200k`.** Cleaner, but published only as Parquet, which needs `pyarrow`.
- **Synthetic prompts.** Reproducible with no download, but less like chat. The author chose a public dataset.
- **One directory per repeat.** C5 says one directory per run. Three directories per configuration would make every reader group them again. The `repeat` field keeps them apart inside one file.
- **The OpenAI SDK as the client.** It hides chunk arrival behind its own parsing. Raw SSE over `httpx2` timestamps each chunk as it arrives and drives any target the same way.
- **`powermetrics` text format.** Its layout changes between macOS releases. The plist format has keys.
- **Recording conditions without refusing.** The author chose to refuse full runs: a run on battery costs a rerun anyway.

## Consequences

- matplotlib joins the dev dependency group for the chart (rule 13).
- `bench/` is checked by ruff and mypy like `src/`, `tests/` and `scripts/`.
- M1-T7 adds a target per baseline by passing its launch command. It needs no harness change.
- Poisson open-loop arrivals (B3) come with M2-T6. KV utilisation and prefix hit rate in summaries come once `/metrics` exists (M2-T5).
- Workload A depends on one Hugging Face file at a pinned revision. If it disappears, the committed `a.json` still runs. Only regeneration needs it.
